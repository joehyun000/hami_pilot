# HAMi 사용량 제한과 느린 추론 요청에 관한 파일럿 실험설계안

> 작성일: 2026-08-10
>
> 상태: 사용자 검토용 1차 확정안
>
> 이 문서의 목적: 실제 GPU 실험을 시작하기 전에 무엇을 왜 비교하고, 어떤 결과일 때 연구를 계속할지 명확히 한다.

## 1. 한 문장으로 설명하는 실험

> 평균 요청량은 설정된 GPU 사용 한도 안에서 충분히 처리할 수 있는데도, HAMi가 사용량을 제한하는 과정에서 실행 대기가 생겨 일부 추론 요청의 응답시간이 유난히 길어지는지 확인한다.

이 파일럿은 “HAMi는 나쁘다”를 증명하는 실험이 아니다. 다음 두 가지를 적은 비용으로 판단하는 실험이다.

1. 확인하려는 현상이 실제로 존재하는가?
2. 더 정밀한 원인 분석에 시간과 GPU를 투입할 만큼 크고 반복 가능한가?

## 2. 이 실험에서 사용하는 말

| 이 문서의 표현 | 뜻 | 코드·논문에서 볼 수 있는 표현 |
|---|---|---|
| 측정 대상 작업 | 응답시간을 관찰하는 BERT 작업 | victim |
| 이웃 작업 | 같은 GPU에서 함께 실행하는 동일한 BERT 작업 | neighbor |
| GPU 사용 한도 | 한 작업이 사용할 수 있는 GPU 연산량의 상한 | compute quota |
| 실행 대기 | HAMi가 사용 한도를 맞추기 위해 GPU 작업 실행을 잠시 보류한 것 | quota wait |
| 느린 요청 구간의 응답시간 | 전체 요청의 99%가 이 시간 안에 끝나는 경계 | p99 latency |
| 한 차례의 실험 | 한 조건을 준비부터 측정 종료까지 실행한 단위 | run |

문서와 발표에서는 왼쪽 표현을 먼저 사용한다. 코드의 설정명이나 결과 파일을 설명할 때만 오른쪽 표현을 괄호로 덧붙인다.

## 3. 연구 배경과 의심하는 원인

GPU를 여러 작업이 함께 사용하면 다음 문제가 생길 수 있다.

- 작업들이 같은 GPU 연산 자원과 메모리 자원을 두고 경쟁하면서 느려질 수 있다.
- 일부 작업이 GPU를 과도하게 사용해 다른 작업의 실행 기회를 줄일 수 있다.

HAMi는 작업별 GPU 사용량에 한도를 두어 과도한 독점을 줄이려고 한다. 그러나 사용 한도를 적용하는 과정에서 GPU 작업의 실행을 잠시 기다리게 할 수 있다.

이번 파일럿이 확인하려는 가설은 다음과 같다.

> 전체 요청을 처리할 능력은 충분하지만, HAMi가 사용량을 제한하면서 만든 일시적인 실행 대기가 느린 일부 요청의 응답시간에 반복 가능한 변화를 만들 수 있다.

변화는 악화만을 뜻하지 않는다. 이웃의 독점을 막아 느린 요청을 줄이는 보호 효과가 나타날 가능성도 열어 둔다.

## 4. 이번 파일럿에서 확인하지 않는 것

다음 결과는 이번 연구의 핵심 결과가 아니다.

- GPU를 100% 쓰던 작업에 50%만 허용했더니 전체적으로 느려졌다는 당연한 결과
- 처리 능력보다 많은 요청을 보내 요청이 계속 쌓이면서 느려진 결과
- 이웃 작업과의 일반적인 GPU 경합만 확인한 결과
- 합성 작업에서만 나타나고 공개 추론 작업에서는 재현되지 않는 결과
- 한 번의 실험에서만 우연히 크게 튄 응답시간

## 5. 왜 다섯 조건을 비교하는가

느린 요청이 발생했을 때 원인을 하나씩 구분하기 위해 다섯 조건을 사용한다.

| 조건 | HAMi 연결 | 측정 대상 작업의 사용 한도 | 이웃 작업 | 확인하려는 것 |
|---|---|---:|---|---|
| C0 기준 | 없음 | 없음 | 없음 | HAMi가 없을 때의 원래 응답시간 |
| C1 라이브러리만 | 있음 | 100% | 없음 | HAMi를 연결하는 것 자체의 추가 비용 |
| C2 사용 한도만 | 있음 | 50% | 없음 | 이웃이 없어도 사용량 제한 과정에서 생기는 영향 |
| C3 이웃만 | 있음 | 100% | 동일 BERT, 100% | 실행 대기 없이 이웃과 GPU를 함께 쓰는 영향 |
| C4 사용 한도와 이웃 | 있음 | 50% | 동일 BERT, 50% | 실제 공유 상황에서 사용량 제한과 이웃이 함께 만드는 영향 |

### 조건이 제대로 만들어졌는지 확인하는 기준

- C1과 C3에서는 측정 대상 작업의 HAMi 실행 대기가 0이어야 한다. C3의 이웃 작업에서도 실행 대기가 없어야 한다.
- C2와 C4에서는 측정 대상 작업의 HAMi 실행 대기가 실제로 발생해야 한다. C4의 이웃 작업 기록은 측정 대상과 분리해 저장한다.
- C0를 제외한 네 조건은 같은 HAMi 실행 경로와 같은 측정 장치를 사용해야 한다.
- C0는 다른 요소를 바꾸지 않고 HAMi 라이브러리 연결만 제거해야 한다.

이 기준을 만족하지 못하면 성능 결과를 해석하지 않고 실험 설정부터 수정한다.

## 6. 어떤 조건끼리 비교하는가

### 연구 질문에 직접 답하는 비교

1. **C2와 C1 비교**

   이웃이 없는 상태에서 GPU 사용 한도를 적용했을 때 느린 요청 구간의 응답시간이 어떻게 달라지는지 본다.

2. **C4와 C3 비교**

   이웃이 있는 상태에서 GPU 사용 한도를 적용했을 때 느린 요청 구간의 응답시간이 어떻게 달라지는지 본다.

이 두 비교에서 반복적인 변화가 나타나야 HAMi 사용량 제한을 중심으로 연구를 계속할 근거가 생긴다.

### 원인을 해석하기 위한 보조 비교

- **C1과 C0 비교:** HAMi 라이브러리 연결 자체의 추가 비용
- **C3과 C1 비교:** 사용량 제한 대기가 없는 일반적인 이웃 작업 경합
- **C4와 C2 비교:** 사용 한도가 있는 상태에서 이웃 작업이 추가한 영향

C3과 C1 사이에서만 느려진다면 일반적인 GPU 공동사용 문제를 확인한 것이며, HAMi 사용량 제한 연구를 지지하는 결과는 아니다.

## 7. 실행 작업을 하나로 고정하는 이유

측정 대상 작업과 이웃 작업은 모두 MLPerf Inference의 BERT-Large SQuAD Server 참조 작업을 사용한다.

- 모델, 데이터, 요청 생성 방식이 공개돼 다른 사람이 재현하기 쉽다.
- 실제 CUDA 연산이 포함된 온라인 추론 형태의 작업이다.
- 측정 대상과 이웃을 같은 작업으로 두면 모델 차이가 결과에 섞이지 않는다.
- C3와 C4에서는 이웃 작업에도 측정 대상 작업과 같은 초당 요청 수를 보낸다.

이 실험은 공식 MLPerf 성능 제출이 아니다. MLPerf의 공개 BERT 작업을 연구용으로 사용하는 것이다.

### 요청이 들어오는 방식

평균 초당 요청 수는 고정하지만, 각 요청의 도착 간격은 서버 환경처럼 불규칙하게 만든다. 앞 요청이 끝날 때까지 기다린 뒤 다음 요청을 보내는 방식은 사용하지 않는다. 따라서 장시간 평균 요청량은 사용 한도 안에 있어도 짧은 순간에는 요청이 몰릴 수 있다.

이번 연구는 바로 이 상황에서 HAMi의 사용량 제한이 순간적인 실행 대기를 만들고, 그 대기가 느린 일부 요청에 나타나는지 확인한다. 모든 조건은 같은 요청 도착 방식과 같은 평균 초당 요청 수를 사용한다.

## 8. 가장 중요한 준비: 요청량 찾기

### 잘못된 요청량 설정

제한이 없는 기준 조건이 감당할 수 있는 요청량의 70%를 그대로 사용하는 방식은 적절하지 않다. 예를 들어 제한 없는 조건이 초당 100건을 처리할 수 있는데 50% 사용 한도를 적용한 조건에 초당 70건을 보내면, 요청이 쌓이면서 느려지는 것이 예정된 결과가 될 수 있다.

이 경우 일반적인 요청 적체와 HAMi의 실행 대기가 얽혀 원인을 구분하기 어렵다.

### 이번 설계의 요청량 선택 방법

1. C2와 C4에서 낮은 초당 요청 수부터 단계적으로 높인다. C4에서는 측정 대상과 이웃에 같은 후보 요청량을 각각 보낸다.
2. 각 요청량에서 다음을 확인한다.
   - 보낸 요청의 98% 이상을 정상적으로 처리하는가?
   - 시간이 지나도 처리 대기 중인 요청이 계속 늘어나지 않는가?
   - 실험 후반으로 갈수록 응답시간이 계속 증가하지 않는가?
   - 시간 초과, 실패, GPU 메모리 부족이 없는가?
3. C2와 C4가 모두 안정적으로 처리할 수 있는 최대 요청량 중 더 낮은 값을 기준으로 삼는다.
4. 그 값보다 여유 있게 낮은 요청량을 후보로 선택한다. 초기값은 60~70% 범위에서 정하되, 이 비율을 보편적인 기준으로 주장하지 않는다.
5. 선택한 요청량에서 C2와 C4의 HAMi 실행 대기가 실제로 발생하는지 확인한다.
6. 요청은 쌓이지 않지만 실행 대기는 발생하는 지점을 최종 요청량으로 정한다.
7. 최종 요청량을 C0~C4에 모두 동일하게 사용한다.

안정적으로 처리하면서 실행 대기도 발생하는 지점을 찾지 못하면, 요청을 과도하게 보내 억지로 현상을 만들지 않는다. 그 경우 현재 모델·사용 한도·요청 형태에서는 가설을 판단할 조건을 만들지 못했다고 기록한다.

## 9. 측정 장치의 영향 확인

HAMi의 실행 대기를 기록하기 위해 코드를 수정한 측정용 라이브러리를 사용한다. 측정 장치가 성능을 바꾸면 결과를 믿을 수 없으므로 다음을 본 실험 전에 확인한다.

- 원본 HAMi 라이브러리와 측정용 HAMi 라이브러리를 C1 조건에서 번갈아 세 쌍 실행한다.
- 느린 요청 구간의 응답시간 차이의 가운데 값이 5%를 넘으면 본 실험을 중단한다.
- 5%는 측정 장치가 완전히 영향이 없다는 뜻이 아니라, 파일럿 진행 여부를 정하기 위한 허용 기준이다.

C1과 C0의 차이에는 허용 범위 안의 측정 장치 비용이 일부 포함될 수 있다. 따라서 이를 “순수한 라이브러리 비용”이라고 과장하지 않고 “HAMi 연결 경로의 추가 비용”이라고 표현한다.

## 10. 무엇을 기록하는가

### 요청별 기록

- 요청 도착 시각
- 요청 완료 시각
- 개별 응답시간
- 성공·실패 여부

### 한 차례의 실험에서 계산할 값

- 전체 요청의 가운데 응답시간
- 전체 요청의 99%가 이 시간 안에 끝나는 응답시간 경계
- 가장 느린 1% 요청들의 응답시간 분포
- 미리 정한 응답시간 목표가 있다면 목표를 넘긴 요청의 비율
- 보낸 요청 수, 완료 요청 수, 초당 완료 요청 수
- 시간에 따라 처리 대기 중인 요청이 늘어나는지 여부

### HAMi와 GPU 기록

- HAMi가 사용량 제한 기능을 확인한 횟수
- 실제로 실행을 기다리게 한 횟수
- 실행 대기의 누적 시간
- GPU 사용률과 메모리 사용량
- GPU 온도와 동작 속도
- GPU, 드라이버, CUDA, HAMi 버전과 고정된 소스 번호

개별 요청의 긴 응답과 HAMi 실행 대기의 정확한 시간 관계는 현재의 누적 측정만으로 완전히 증명할 수 없다. 파일럿에서는 한 차례의 실험 단위에서 두 현상이 함께 반복되는지 판단하고, 연구를 계속하기로 한 뒤 요청 단위 시간 연결 계측을 추가한다.

## 11. 실험 순서

### 1단계: 환경 확인

- 다른 작업이 GPU를 사용하지 않는지 확인한다.
- Docker, CUDA, 모델, 데이터, 소스 버전과 실행 이미지를 확인한다.
- GPU 온도와 동작 속도 설정을 기록한다.

### 2단계: 측정 장치 영향 확인

- C1에서 원본·측정용 HAMi 라이브러리를 세 쌍 교차 실행한다.
- 추가 비용이 5%를 넘으면 측정 장치를 수정한다.

### 3단계: 요청량 찾기

- C2와 C4에서 여러 초당 요청 수를 시험한다.
- 요청 적체는 없지만 HAMi 실행 대기는 발생하는 요청량을 선택한다.

### 4단계: 조건 확인용 짧은 실험

- C1과 C3의 실행 대기가 0인지 확인한다.
- C2와 C4의 실행 대기가 0보다 큰지 확인한다.
- 모든 조건이 같은 요청량을 정상적으로 처리하는지 확인한다.

### 5단계: 본 실험

- 다섯 조건을 한 묶음으로 구성한다.
- 묶음마다 다섯 조건의 실행 순서를 무작위로 바꾼다.
- 다섯 묶음을 실행한다.
- 총 본 실험 횟수는 5조건 × 5묶음 = 25회다.
- 각 조건은 모델 준비 후 60초 동안 안정화하고, 이어서 300초 동안 측정한다.
- 이웃 작업이 있는 조건에서는 이웃을 먼저 시작하고 측정 대상 작업이 끝날 때까지 계속 실행한다.
- 안정화 시간과 측정 시간은 모든 조건에서 동일하게 유지한다.

한 묶음의 예시는 다음과 같다.

```text
1묶음: C3 → C0 → C2 → C4 → C1
2묶음: C1 → C4 → C0 → C3 → C2
...
5묶음: 무작위 순서
```

요청 수가 많더라도 요청 하나를 독립적인 반복 실험으로 세지 않는다. 조건 하나를 처음부터 끝까지 실행한 한 차례의 실험을 반복 단위로 사용한다.

## 12. 결과 판정

### 먼저 실험이 유효한지 판단한다

다음 중 하나라도 발생하면 연구 가설을 판단하지 않는다.

- 측정 장치의 추가 비용이 5%를 넘는다.
- C1 또는 C3에서 HAMi 실행 대기가 발생한다.
- C2와 C4에서 HAMi 실행 대기가 발생하지 않는다.
- 요청이 시간이 지날수록 계속 쌓인다.
- 조건별 완료 요청량이 목표 요청량과 크게 다르다.
- 실패, 시간 초과, GPU 메모리 부족 또는 재시작이 발생한다.

이 경우 결과는 “가설이 틀림”이 아니라 “실험 조건이 유효하지 않음”으로 기록한다.

### 연구 계속

C2와 C1의 비교 또는 C4와 C3의 비교에서 다음을 모두 만족한다.

- 다섯 묶음 중 네 묶음 이상에서 같은 방향의 변화가 나타난다.
- 느린 요청 구간의 응답시간 변화 가운데 값이 10% 이상이다.
- 사용 한도 적용 조건에서 HAMi 실행 대기가 실제로 기록된다.
- 요청 적체 없이 모든 조건이 목표 요청량을 처리한다.

10%는 논문의 통계적 유의성 기준이 아니다. 더 정밀한 계측과 추가 GPU 실험에 자원을 투입할지를 정하기 위한 파일럿 내부 기준이다.

응답시간이 10% 이상 증가하면 제한 비용을, 10% 이상 감소하면 보호 효과를 중심으로 후속 연구를 설계한다.

### 제한적으로 계속

- HAMi 실행 대기와 같은 방향의 응답시간 변화가 네 묶음 이상에서 반복되지만 변화 크기가 10% 미만이다.
- 이 경우 사용 한도나 요청량 경계 조건을 한 차례만 추가 탐색한다.

### 현재 방향 중단

- 일반적인 이웃 작업 경합만 나타나고 C2 대 C1, C4 대 C3에서는 반복적인 변화가 없다.
- HAMi 실행 대기는 발생하지만 느린 요청 구간의 응답시간과 반복 가능한 관계가 없다.
- 유효한 실험 조건에서 결과 방향이 계속 바뀐다.
- 공개 BERT 작업에서는 현상이 나타나지 않고 합성 작업에서만 나타난다.

## 13. 결과별 다음 단계

| 파일럿 결과 | 해석 | 다음 행동 |

| 사용 한도가 느린 요청을 반복적으로 감소시킴 | 이웃 독점을 막는 보호 효과 가능성 | 보호 효과가 나타나는 부하·사용 한도 경계를 찾는다. |

| 이웃 작업 경합만 확인 | HAMi 고유 영향은 약함 | 현재 HAMi 중심 연구를 중단한다. |
| 실행 대기 자체가 없음 | 확인하려는 원인이 실험에서 만들어지지 않음 | 설정을 점검하되 과부하로 현상을 억지로 만들지 않는다. |
| 실험 결과가 불안정 | 측정 환경 또는 현상이 불안정 | 원인을 한 번 점검하고 반복되지 않으면 중단한다. |

## 14. 현재 구현과 달라지는 점

현재 하네스는 네 조건과 총 20회의 본 실험을 전제로 작성돼 있다. 이 설계안을 실행하려면 다음 변경이 필요하다.

1. HAMi를 연결하지 않은 C0를 추가해 다섯 조건으로 바꾼다.
2. 기존 P0~P3 이름을 C1~C4 의미에 맞게 정리한다.
3. 조건당 다섯 번, 총 25회의 무작위 묶음 실행으로 바꾼다.
4. 제한 없는 단독 조건에서 요청량을 정하는 현재 보정 방식을 폐기한다.
5. C2와 C4의 안정적인 처리 능력을 기준으로 공통 요청량을 정한다.
6. 현재 요약값 중심 기록을 요청별 도착·완료 시각 기록으로 확장한다.
7. 요청 적체 여부와 시간에 따른 응답시간 증가를 기록한다.
8. 일반적인 이웃 경합만으로 연구 계속 판정이 나지 않도록 비교 규칙을 바꾼다.
9. 응답시간 증가뿐 아니라 보호 효과에 해당하는 감소도 판정한다.
10. 보고서의 영어 중심 용어를 이 문서의 한국어 표현으로 바꾼다.

이 문서가 승인되기 전에는 하네스 코드를 수정하거나 실제 GPU 본 실험을 실행하지 않는다.
