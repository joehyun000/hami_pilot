# 7월 28일 주제와 현재 파일럿의 관계

## 한 문장 답변

> 7월 28일은 compute quota가 없는 NVIDIA time-slicing에서 요청량과 실제 사용량이 어긋나는 문제를 다뤘고, 현재는 그 문제를 줄이기 위한 HAMi compute quota가 어떤 실행 비용을 만드는지 검증합니다. 반대 주장이 아니라 무제어 공유의 문제와 제어 비용을 순서대로 묻는 연구입니다.

## 무엇이 달라졌나

| 구분 | 7월 28일 | 현재 파일럿 |
|---|---|---|
| 대상 시스템 | NVIDIA Kubernetes time-slicing | HAMi `gpucores` / HAMi-core rate limiter |
| compute quota | 없음 | 있음: 50% 또는 대기 없는 100% 경로 |
| 질문 | 같은 GPU 요청이 같은 실제 몫을 보장하는가 | quota를 거는 과정의 자기 대기와 공동배치 경합을 구분할 수 있는가 |
| 당시/현재 증거 | CUDA process 수준 예비실험 | HAMi 소스 확인 + MLPerf 기반 파일럿 하네스, 실제 GPU 결과는 아직 없음 |
| 논문에서의 역할 | 문제 배경 | 검증 대상인 본 연구 가설 |

## 무엇이 맞고 무엇을 철회해야 하나

- “time-slicing에는 Pod별 compute quota가 없다”와 “HAMi는 compute quota를 제공한다”는 서로 다른 시스템에 대한 설명이므로 둘 다 성립할 수 있다.
- 7월 28일 CUDA process 실험을 Kubernetes Pod 또는 HAMi 결과처럼 일반화하면 안 된다.
- 파일럿 전에는 “HAMi가 tail latency를 악화시킨다”고 말할 수 없다. 현재 허용되는 표현은 “그 가능성을 표준 workload에서 검증한다”이다.
- HAMi v2.9.0이 고정한 HAMi-core `5091a2f…`를 확인한 결과 watcher는 `nvmlDeviceGetProcessUtilization`과 등록 PID 필터를 사용한다. 따라서 이 버전에서 이웃 부하가 Victim의 관측 사용률을 직접 올리는 device-wide 교차 제어 주장은 제외한다.

## 더 나아진 점

1. 시스템 이름과 제어 메커니즘을 분리해 반대 주장처럼 보이던 문제를 해소했다.
2. 합성 kernel만이 아니라 MLPerf BERT Server라는 공개 실행 workload를 1차 증거로 사용한다.
3. P0~P3와 block 반복으로 자기 quota 비용과 공동배치 효과를 조건 차이로 구분한다.
4. 소스 가설을 결과처럼 말하지 않고 probe wait와 p99가 실제로 관측돼야만 GO로 판정한다.

## 더 위험해진 점

1. device-wide 교차 제어라는 강한 신규 주장은 소스와 맞지 않아 사라졌다. 학술 기여는 더 정직하지만 범위가 좁어졌다.
2. HAMi 자체 비용이 10% 미만이거나 반복 방향이 흔들리면 연구의 중심 가설이 약해질 수 있다.
3. probe가 p99를 5% 넘게 바꾸면 측정 결과를 사용할 수 없다. 이를 위해 vanilla/probe image를 별도로 비교한다.
4. 한 GPU·한 BERT workload의 파일럿은 일반화가 아니라 후속 연구 투자 여부만 판정한다.

## 교수님께 설명할 순서

1. 7월 28일과 현재는 같은 시스템이 아니었다고 먼저 명확히 한다.
2. 공통 문제를 “GPU를 공유할 때 기대한 몫과 실제 실행이 어긋날 수 있다”로 제한한다.
3. 7월 28일은 무제어 공유, 현재는 제어 비용이라는 연속된 질문임을 설명한다.
4. 아직 결과가 아니라 파일럿 가설이며, NO-GO도 허용하는 기준을 제시한다.
